# CEO Plan: Production Gap Closure

## Vision

The take-home app moves from a strong single-case verifier into a production-grade review system for batch alcohol-label compliance. Vercel remains the reviewer-facing product front door, while a dedicated worker service owns long-running batch processing, retries, durable status, retention cleanup, and AI execution. The core product promise becomes: upload a 200-300 case batch, leave the tab, return later, and land on a trustworthy triage queue with recoverable evidence for every case.

### 10x Check

The 10x version is not merely "support 300 files." It is the reviewer's morning queue: the system catches intake issues before processing, turns every case into a durable job, orders red and amber cases first, preserves green cases for audit, and lets a reviewer understand the evidence trail without spelunking through model output. Admins can see whether the processing line is healthy, reassign work, recover failed cases, and export a complete 90-day audit record.

### Platonic Ideal

A reviewer starts with a batch, not a form. Before the run begins, the app explains which applications and labels are paired, which files are malformed, how many cases will be processed, and what the expected cost/time looks like. Processing continues outside the browser. When the reviewer returns, the queue has already done the first pass: mismatches and uncertain warnings are at the top, clean matches remain openable, and every case has a readable evidence timeline. The machine is clearly advisory; the human disposition is clearly authoritative.

The architecture should feel boring in the best way: typed contracts at every boundary, idempotent jobs, object storage for source files and evidence crops, relational records for batch/case/status/disposition state, queue-backed worker execution, structured logs and trace IDs, and retention cleanup that can be inspected rather than guessed at.

## Accepted Scope

- Vercel reviewer/admin UI and API front door.
- Dedicated worker service for durable batch processing, LLM calls, retries, file/evidence processing, retention cleanup, and export generation.
- Durable object storage for uploaded files, generated evidence crops, exports, and retained audit artifacts.
- Relational data model for batches, cases, case files, processing attempts, extracted fields, verdicts, warning evidence, dispositions, assignments, exports, and retention state.
- Batch Intake Concierge with manifest support, file pairing, duplicate detection, unsupported-file rejection, preflight summary, and estimated cost/time.
- Triage-first queue containing every case, ordered red, amber, green while preserving search/open/export for clean matches.
- Per-case Evidence Timeline with source files, extraction result, deterministic matching verdict, confidence/uncertainty signals, retry/error history, warning evidence, disposition, and export history.
- Reviewer Work Assignment with assigned batches, unassigned/all admin views, reassignment, workload filters, and ownership status.
- Government Warning typography handling that rejects clear text/capitalization failures, routes uncertain boldness to needs-review, and shows visual warning evidence where available.
- Compliance Ruleset Versioning for engine version, prompt version, model name, extraction schema version, warning policy version, and code commit.
- Operations Console for queue depth, stuck/failed jobs, retry controls, worker heartbeat, retention cleanup status, storage usage, and export/replay links.
- 90-day audit archive with automatic purge unless protected by admin policy.
- Exports that include every case, including clean matches, failed cases, and pending-review cases.
- Documentation for Azure/FedRAMP migration and cloud AI/provider swap path without claiming current government-production compliance.

## Deferred To Later

- Enterprise SSO and government identity provider integration.
- Direct COLA system integration or write-back.
- Permanent legal system-of-record retention beyond the 90-day archive.
- Applicant/importer self-service portal.
- Fully offline or government-network-only deployment.

## NOT In Scope

- Automatic legal approval without reviewer accountability.
- Pixel-perfect forensic font analysis as a replacement for human review on low-quality images.
- Rebuilding the deterministic matching engine outside `lib/engine`.
- Moving the entire Next.js UI off Vercel in this phase.

## Dream State Delta

Current state: a strong prototype verifies single cases and generated demo batches, with honest documentation about client-side fan-out and missing persistence.

This plan: introduces a durable split-worker product layer that can recover 200-300 uploaded application/label cases, preserve audit evidence, route uncertain warning typography to humans, and give admins operational control.

12-month ideal: a government-ready review platform with approved identity, environment-specific AI/provider routing, formal retention/legal policy, deep observability, and integration points for official COLA systems while preserving human accountability.

## Temporal Decisions

- **Worker deployment target:** fast prototype worker first. The worker should still be containerized and portable, but the first deployment should optimize for speed and demo reliability rather than immediate Azure alignment.
- **Worker artifact contract:** the worker is a first-class deployable with an explicit source directory, local run command, build command, Dockerfile or host-specific deployment path, health endpoint, environment contract, and staging/production deployment steps.
- **Queue backbone:** Vercel Queues first, wrapped behind a queue adapter, with idempotent per-case jobs, database-backed status, retry counters, and replay controls. Because Vercel Queues is currently beta, the plan must document beta limits and a fallback queue/workflow provider before implementation starts.
- **Auth depth:** Auth.js/NextAuth-style app authentication first, with users/roles in Postgres, seeded reviewer/admin users for demo and staging, assigned-batch scoping, and disposition identity capture. Keep an adapter seam for later enterprise/government SSO.
- **Storage provider:** Vercel Blob first for raw uploads, warning crops, and exports. Persist provider, bucket/container, object key, checksum, size, content type, and retention metadata so a later object-store migration is documented and mechanically possible.
- **Database shape:** managed Postgres shared by Vercel API routes and the worker service, with explicit transactions, foreign keys, indexes, and append-style audit events for sensitive changes.
- **Database connection strategy:** define the Vercel function DB client pattern, worker pool size, max concurrent DB-using jobs, transaction boundaries, and staging load check for connection exhaustion before enabling 300-case batches.
- **Shared database ownership:** Vercel owns intake, assignment, reviewer disposition, and admin actions. The worker owns processing attempts, extraction, verdicts, warning evidence, retry state, retention cleanup, and export generation. Batch/case summary status may only change through the documented state machine.
- **Warning typography strategy:** hybrid model judgment plus evidence crop. The model returns warning text, region, lead-in/body segmentation, boldness confidence, and uncertainty reason; the app stores the crop and routes low confidence to needs-review.
- **Workflow safety:** batch and case lifecycle states must be first-class shared typed state machines with allowed transitions, invalid-transition tests, and enforcement at API/worker mutation boundaries.
- **Internal trust boundary:** Vercel API, worker service, queue provider, object storage, and database access must use service-to-service auth: scoped secrets, provider signature verification or signed job payloads, scoped database credentials where practical, and audit logs for internal mutations.
- **Rollout posture:** durable batch ships behind a feature flag. The current single/small-upload path stays available during rollout; disabling the flag stops new durable batches while existing queued jobs drain, pause, or are replayed through admin controls.
- **Failure finalization:** after bounded retries, an unrecoverable case becomes an explicit failed or needs-better-image row with error class, reason, attempt count, timestamps, triage visibility, and export inclusion.
- **Malformed AI output:** all model output remains parsed through `lib/contract.ts`. Malformed, empty, refusal, or schema-invalid responses receive bounded retries, then become visible needs-review or failed states with safe raw-error capture and no misleading score.
- **Poison jobs:** jobs that exhaust bounded attempts move to dead-letter state with payload/error history preserved. Admins can replay after repair, and affected cases remain visible in triage/export rather than looping silently.
- **Storage consistency:** each stored object has a manifest row with checksum, size, content type, provider, object key, expected lifecycle state, and retention metadata. Reconciliation detects missing/orphaned blobs and surfaces repair/delete actions in the operations console.
- **Retention purge:** retention cleanup is two-phase: mark records purge-eligible and show preview/counts, then delete/redact retrievable archive data while preserving minimal tombstones for deletion audit unless policy later requires full erasure.
- **File access security:** source files, crops, and exports are accessed through short-lived scoped signed URLs generated only after app-level authorization checks. Signed URLs are never stored as durable evidence, and access is logged.
- **Authorization model:** every batch, case, file, export, assignment, and disposition access passes through central aggregate-level authorization. Reviewer access is scoped to assigned batches; admin access is broader but still logged.
- **Prompt injection posture:** uploaded application and label text is untrusted evidence, never instructions. Extraction prompts must say so explicitly, deterministic scoring remains outside the model, all output is zod-validated, and adversarial prompt-injection fixtures are added to evals/tests.
- **Admin replay controls:** job replay requires admin authorization, eligibility checks, a reason note, rate limiting, append-only processing attempts, and audit log entries. Replay never overwrites prior evidence in place.
- **Idempotent intake:** batch intake uses an intake session with an idempotency key, manifest hash, upload status, and a single allowed transition into processing so refresh/retry/double-submit cannot enqueue duplicate batches.
- **Resumable uploads:** the intake manifest tracks every expected file and its uploaded, missing, invalid, duplicate, or excluded state. Processing is blocked until required pairs are complete or explicitly excluded, and uploaded files can resume by checksum/object key.
- **Assignment concurrency:** reviewer/admin assignment changes use optimistic concurrency with assignment versions, stale-view warnings, and optional reviewer claim leases for active case work.
- **Export semantics:** exports are point-in-time snapshot records with timestamp, requester, included case IDs/statuses, ruleset versions, completion/partial label, and a stable generated artifact.
- **Shared core boundary:** contracts, deterministic engine code, workflow state machines, and shared validators must live behind a worker-safe core boundary with no Next.js imports. The worker must not duplicate schemas or scoring rules.
- **Persistence organization:** use repository/service modules per aggregate: batches, cases, files, jobs, dispositions, exports, retention, assignments, and audit events. Route/job handlers call these modules rather than scattering direct DB writes.
- **Transaction ownership:** use-case/service-command modules own transaction orchestration. Aggregate repositories accept an explicit transaction context, and state changes plus audit events for a use case commit in the same unit of work.
- **Contract organization:** preserve `lib/contract.ts` as a compatibility barrel and public typed contract export point. Split expanded schemas into domain files for verification, batch, archive, auth, worker payloads, and admin operations without broad import churn in the first split PR.
- **Test base:** add fast Vitest coverage for expanded contracts, worker payload schemas, warning evidence schema, role/disposition validation, and batch/case state machines including invalid transitions.
- **Adapter contract tests:** storage, queue, and model adapters must share behavior-level contract tests. Fake/local adapters and real staging adapters must satisfy the same semantics for missing objects, metadata, retries, signed access, enqueue/dequeue, and malformed model output.
- **Worker integration tests:** add a local harness with test Postgres, fake queue adapter, fake Blob adapter, and model stubs that exercises success, retry, malformed output, dead-letter, replay, and failed-case finalization.
- **Workflow E2E tests:** add Playwright coverage for login/roles, intake preflight, partial upload recovery, triage ordering, case evidence timeline, dispositions, admin replay, operations console failures, and export download.
- **Required E2E smoke set:** before the durable batch path is considered shippable, Playwright must cover reviewer login/work queue, resumable intake, 300-case stubbed durable processing to triage, reviewer disposition plus export, and admin dead-letter replay plus operations health.
- **AI eval gate:** keep `npm run verify` deterministic with offline fixtures, and add optional `eval:live` cases for warning typography uncertainty, malformed/low-quality images, prompt-injection text, and real model schema behavior.
- **Live eval release thresholds:** `eval:live` must have blocking thresholds for schema-valid model output, no prompt-injection compliance bypass, exact warning text/capitalization behavior, and routing uncertain typography to needs-review. Compare live results against committed offline fixtures and the last accepted live baseline.
- **Migration and rollback tests:** add tests or scripted checks for add-only migration compatibility with old/new code assumptions, feature-flag-off behavior, runtime kill switches, retention purge preview, and smoke rollback path.
- **Concurrency budget:** define configurable per-stage limits for intake finalization, extraction/model calls, scoring, evidence storage, export generation, and replay. Surface queue depth, active counts, retry counts, and rate-limit pressure in ops views.
- **Latency targets:** keep single-case verification at the existing <=5s p50 target when provider conditions allow. Initial prototype SLOs: 300-case manifest preflight <=10s, first durable result <=60s, 50-case batch completion <=10 minutes, and 300-case batch completion <=45 minutes in staging stub/live-limited mode. Tune these after real measurements.
- **Spend and concurrency budgets:** model-call concurrency and daily/batch spend caps must be configurable before enabling 300-case durable batches.
- **Index plan:** first schema includes query-driven indexes for batch owner/status/created_at, case batch/status/severity/assignment, job state/next_attempt_at, file retention/object key, export batch/created_at, audit event aggregate/time, and purge eligibility.
- **Triage rendering:** use cursor pagination or virtualization with lightweight rows, lazy-loaded evidence timelines, stable row heights, and debounced live updates so 300-case queues remain fast to scan. Sort by severity bucket, status priority, updated time, and case ID; live updates should show refresh markers rather than reshuffling the current viewport.
- **Traceability:** propagate batch ID, case ID, intake session ID, job ID, processing attempt ID, export ID, and request trace ID through logs, queue payloads, DB rows, object metadata, and model-call metadata.
- **Product health metrics:** operations console shows queue depth, oldest job age, failure/retry/dead-letter rates, stuck batch count, warning needs-review count, export failures, retention overdue count, worker heartbeat, and estimated model spend.
- **Audit events:** sensitive actions write append-only audit events with actor, action, aggregate type/id, before/after summary where safe, reason note, timestamp, trace ID, and source IP/user agent when available.
- **Runbooks and alerts:** define alert thresholds and response runbooks for stuck jobs, dead-letter spikes, worker heartbeat loss, model/rate-limit spikes, export failures, retention overdue, and storage reconciliation drift.
- **Rollout sequence:** deploy add-only database schema and config first, then storage/queue/worker in disabled mode, then feature-flagged API/UI, then enable durable batch for test users before broader rollout.
- **Environment parity:** maintain preview/staging with real worker, staging Postgres, Blob, queue, auth, and model integration under low budget/concurrency limits, plus seeded users and smoke fixtures.
- **Post-deploy smoke:** add automated smoke for a tiny durable batch through intake, Blob, DB, queue, worker, model fixture/live-limited mode, triage update, disposition, export, and operations health.
- **Operational brakes:** document rotation for auth, worker, queue, Blob, database, model, and signing secrets. Add runtime kill switches for durable batch intake, worker processing, model calls, replay, exports, and purge.
- **Provider boundaries:** use small provider adapters for storage, queue, model, and worker configuration. Provider-specific SDK calls stay at the edge, and persisted metadata includes provider/object identifiers needed for migration.
- **Naming trajectory:** use domain-first product names such as batches, cases, warnings, and dispositions in UI/domain code, with reusable primitives such as audit events, object manifests, job attempts, and exports underneath.
- **Government migration roadmap:** documentation must explicitly distinguish current prototype posture from target government posture, covering identity, storage, AI/provider swaps, network controls, audit/logging, retention/legal policy, data migration, and validation gates.
- **Reviewer IA:** authenticated reviewers land on a Work Queue showing assigned batches, urgent red/amber counts, in-progress processing, failed/intake-action-needed batches, and direct entry into the highest-priority queue.
- **Case detail IA:** case detail is decision-first: machine overall verdict, required human action, disposition controls, and key reasons at the top; application-vs-label comparison next; warning evidence next; timeline, source files, retries, and export history below.
- **Warning evidence UI:** show a warning crop, lead-in/body highlights when available, boldness/body confidence, and plain-language explanation for match, mismatch, or needs-review. Avoid advanced forensic editing tools in this phase.
- **Admin IA:** operations console uses focused tabs for Health, Failed/Dead-letter Jobs, Assignments, Exports, Retention, Storage Reconciliation, and Settings/Kill Switches.
- **State design:** define loading, empty, partial, failed, permission-denied, stale, disabled-by-kill-switch, and success states for Work Queue, Intake, Batch Detail, Case Detail, Ops Console, Exports, and Retention.
- **Role-aware app shell:** authenticated users get a persistent operational shell with role-aware navigation. Reviewers see Intake, Work Queue, Case Search, Exports, and Help/Runbooks. Admins additionally see Operations, Assignments, Retention, Storage, and Settings/Kill Switches. Reviewers land on Work Queue; admins land on Operations Health with a direct path back to Work Queue.
- **Screen hierarchy constraints:** every primary screen must make the first three reviewer/admin questions visible without scrolling. Intake shows upload status, pairing/preflight problems, and start/resume action. Work Queue shows priority counts, filtered case table, and active assignment controls. Case Detail shows required human action, top evidence/reasons, and disposition controls. Operations shows system health, failed/dead-letter work, and recovery actions.

### Anti-Generic UI Constraints

- Treat the production UI as a compliance workbench, not a marketing page or decorative dashboard.
- Work Queue is table/list-first: priority counters may sit above it, but the case rows are the main surface.
- Ops Console is operational-table-first: health tiles are compact summaries, while failed jobs, replay eligibility, retention previews, and reconciliation rows carry the work.
- Case Detail is comparison/evidence-first: use a decision header, field comparison rows, warning crop, and timeline rather than stacked summary cards.
- Cards are allowed for repeated case rows, modals, bounded evidence panels, and compact health summaries; do not build page sections as nested or decorative card grids.
- Avoid ornamental icons, colored-circle feature tiles, centered dashboard hero copy, decorative gradients, and repeated three-column feature grids.
- Use utility copy: status, evidence, risk, action, and accountability. Do not use aspirational product copy inside the reviewer/admin workflow.
- Motion should only clarify state changes, progress, row updates, or focus movement; no decorative motion in review-critical screens.

### Responsive And Accessibility Specs

| Area | Desktop | Tablet | Mobile |
|---|---|---|---|

Accessibility acceptance:

- Provide visible labels for every input; placeholders are never the only label.
- Use semantic landmarks for shell, navigation, main content, and complementary evidence/timeline panels.
- Tables/lists support keyboard traversal, sortable/filterable controls, and a visible focus state.
- Tabs, modals, and drawers have focus trapping, Escape behavior, return focus, and screen-reader names.
- Touch/click targets for primary controls are at least 44px in the mobile/tablet layouts.
- Body text and status text meet at least 4.5:1 contrast against their surface.
- Severity is never conveyed by color alone; pair red/amber/green with labels/icons/text.
- Warning crops include text alternatives: extracted warning text, whether lead-in/body segmentation was detected, confidence, and uncertainty reason.
- Live updates use polite announcements for status changes and do not steal focus or reorder the visible viewport without user action.
- Reduced-motion preferences disable decorative motion and preserve progress/state meaning through text.

### Work Queue Row Anatomy

Desktop row columns:

1. Severity/status: red, amber, green, failed, running, or intake-action-needed label.
2. Case identity: batch name/id, case id, brand, class/type, applicant.
3. Issue summary: top mismatch or warning uncertainty in plain language.
4. Evidence cue: warning/crop/confidence icon+label, failed attempt count, or clean-match marker.
5. Assignment: owner, claim/reassign state, stale assignment warning when applicable.
6. Updated time and ruleset/version cue.
7. Primary action: open case, resume intake, request better image, or admin replay where eligible.

Row behavior:

- Keep row heights stable; long evidence summaries truncate to two lines with accessible full text.
- Expandable row detail may show secondary reasons, source-file count, and last attempt summary without leaving the queue.
- Sorting stays stable: severity bucket, status priority, updated time, case ID.
- Live updates mark rows as changed and offer refresh; they do not reshuffle the current viewport automatically.
- Mobile rows collapse to severity/status, case identity, one issue summary, assignment, and one primary action.

### Disposition Interaction Rules

- Disposition controls sit in the Case Detail decision header and repeat as a sticky action group after the evidence sections on long pages.
- Approve is enabled only when required evidence has loaded and assignment is current. A note is optional for clean green cases and required when the reviewer overrides any red/amber machine concern.
- Reject always requires a reason note and shows the fields/evidence that will be included in the audit summary.
- Request better image always requires a reason category, optional free text, and a visible list of affected files or unreadable evidence.
- Needs-review is a system/routing state, not a final human disposition; reviewers resolve it through approve, reject, or request better image.
- Stale assignment or already-dispositioned cases disable final actions until the reviewer refreshes and sees who changed the case.
- Destructive or externally visible actions use a compact confirmation dialog with the action, reason, actor, timestamp, and case ID.
- After saving, the UI shows the recorded disposition, actor, timestamp, reason summary, and export inclusion status in the decision header and evidence timeline.

```text
  -> ready_to_process
  -> processing
  -> partially_failed

  -> archived
  -> purge_eligible
  -> purged

```

```text
draft
  -> queued
  -> extracting
  -> scoring
  -> needs_review
  -> has_mismatches

  -> retry_wait
```

### Error Flow

```text
Job fails
  -> classify error
  -> retry if retryable and attempts remain
  -> dead-letter if poison/exhausted
  -> finalize visible case state when unrecoverable
  -> emit audit/log/metric
  -> show in triage and ops console
```

```text
Issue detected
  -> disable durableBatch flag

  -> pause worker/model/export/purge kill switch if needed
  -> let safe jobs drain or move to dead-letter
  -> keep current single/small-upload path available
  -> repair/replay from ops console after fix
```
